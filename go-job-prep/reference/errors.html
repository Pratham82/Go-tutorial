Go Error Handling — Cheat Sheet

Compressed essence. For the lesson, see Lesson 0001.

The core idea

error is just an interface:

type error interface {
    Error() string
}

Errors are ordinary values. Functions that can fail return one as the last result. The caller checks it. There are no exceptions.

f, err := os.Open("config.yaml")
if err != nil {
    return err            // handle, or hand it up
}
defer f.Close()

Creating errors

FormCodeUse when
Ad‑hocerrors.New("cache miss")One‑off, no one needs to match on it
Formattedfmt.Errorf("id %d: %v", id, err)Need context; caller won't unwrap
Wrappedfmt.Errorf("loading user: %w", err)Add context and let caller unwrap
Sentinelvar ErrNotFound = errors.New("not found")Caller compares with errors.Is
Typedtype ValidationError struct { Field string }Caller needs structured data via errors.As

Inspecting errors (Go 1.13+)

// Is: does the chain contain this specific sentinel value?
if errors.Is(err, sql.ErrNoRows) {
    return nil, ErrNotFound
}

// As: does the chain contain an error of this type? If so, bind it.
var verr *ValidationError
if errors.As(err, &verr) {
    http.Error(w, verr.Field+" is invalid", 400)
}

// Unwrap: one step down the chain (rarely called directly).
inner := errors.Unwrap(err)

// Join: combine several errors (Go 1.20+). Is/As see all of them.
err := errors.Join(err1, err2)

Rule of thumb

Wrap with %w when a caller upstream might reasonably want to detect the underlying cause. Use %v (no wrap) when the underlying error is an implementation detail you don't want to leak into your API's contract.

Custom error type — the full pattern

type ValidationError struct {
    Field string
    Err   error            // optional wrapped cause
}

func (e *ValidationError) Error() string {
    return fmt.Sprintf("validation failed on %s: %v", e.Field, e.Err)
}

func (e *ValidationError) Unwrap() error { return e.Err }  // makes errors.Is/As reach Err

Style rules (from Go Code Review Comments)

  • Error strings are not capitalised and have no trailing punctuation: "cannot parse config", not "Cannot parse config." (they get wrapped inside other strings).
  • Handle an error once. Either log it or return it — not both.
  • Add context as it goes up: fmt.Errorf("loading user %d: %w", id, err).
  • Don't panic for ordinary failures. panic is for programmer bugs / truly unrecoverable state.
  • Name the variable err. Check it immediately, on the next line.

Decision flow

function can fail?
  └─ return error as last value
       caller: can it do something useful about it?
         ├─ yes → handle here (retry, default, translate to HTTP status)
         └─ no  → add context with %w and return it upward
       at the top (main / HTTP handler):
         └─ log it once (structured), return a clean message to the user
