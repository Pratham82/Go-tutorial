Errors are values

The win: by the end you can look at any Go error and pick the right tool to inspect it, and wrap your own errors so callers upstream can still do that. This is table stakes in every backend codebase and a routine interview probe. It builds straight on the interface knowledge you just finished in the Tour — because error is an interface.

1. There are no exceptions

In the languages you already know, a failure unwinds the stack until someone catches it. Go does not do this. A function that can fail returns an extra value of type error, and the caller checks it:

f, err := os.Open("config.yaml")
if err != nil {
    return err
}
defer f.Close()

error is the whole contract — a one‑method interface (Error handling and Go):

type error interface {
    Error() string
}

Because an error is just a value, you can store it, compare it, pass it around, and — the key move — wrap it with more context as it travels up.

Convention: the error is the last return value and is named err. You check it on the very next line. Reviewers notice when you don't.

2. Making errors: four shapes

ShapeExampleCaller can…
Ad‑hocerrors.New("cache miss")read the text
With contextfmt.Errorf("user %d: %v", id, err)read the text
Sentinelvar ErrNotFound = errors.New("not found")errors.Is(err, ErrNotFound)
Typedtype ValidationError struct { Field string }errors.As → read Field

Reach for a sentinel when the caller only needs to ask "is it this?". Reach for a typed error when the caller needs data out of it (which field failed, which HTTP status to send).

3. Wrapping: %w vs %v

fmt.Errorf with the %w verb records the original error inside the new one, forming a chain (Working with Errors in Go 1.13):

if err != nil {
    return fmt.Errorf("loading user %d: %w", id, err)   // chain preserved
}

Use %v instead when the inner error is an implementation detail you don't want to become part of your API's promise. %w = "callers may depend on this cause"; %v = "this cause is private".

4. Inspecting: Is and As

// Is — is this specific sentinel anywhere in the chain?
if errors.Is(err, sql.ErrNoRows) {
    return ErrNotFound
}

// As — is there an error of this type in the chain? If so, bind it.
var verr *ValidationError
if errors.As(err, &verr) {
    writeStatus(w, 400, verr.Field+" is invalid")
}

Both walk the whole %w chain for you. You almost never call errors.Unwrap by hand.

To make your typed error transparent to this machinery, give it an Unwrap method:

func (e *ValidationError) Error() string { return "invalid " + e.Field }
func (e *ValidationError) Unwrap() error { return e.Err }

5. Do it once

The most common review comment: handle an error once. Either log it or return it, never both — double‑logging makes production logs lie about how many things failed. Log at the edge (the HTTP handler or main), return everywhere below it.

60‑second exercise

In your go-projects/ area, write this and run it:

package main

import (
    "errors"
    "fmt"
)

var ErrNotFound = errors.New("not found")

func lookup(id int) error {
    if id != 1 {
        return fmt.Errorf("lookup id=%d: %w", id, ErrNotFound)
    }
    return nil
}

func main() {
    err := lookup(42)
    fmt.Println(err)
    fmt.Println("is ErrNotFound?", errors.Is(err, ErrNotFound))
}

Then change the %w to %v and re‑run. Watch the errors.Is line flip to false. That one character is the whole lesson.
